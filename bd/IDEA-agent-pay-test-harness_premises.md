## ② 領域スコープ
- 関連領域: AP2マンデート検証 / agent決済の結合テスト / 異常系シナリオ再現 / 意図適合の判定 / 証拠・適合レポート生成
- 選択スコープ: **エージェント決済の「意図適合」検証ハーネス** — 自然言語の意図(マンデート)を注入し、PayPal sandbox上の実処理が意図に適合したかを検査する
- 選択理由: 発行側(ウォレット6社)・消費者監査側(不能)・紛争処理側(占有)は全て塞がれたが、「採用前に意図通りかを検査する層」はプロトコルが新しいため本物の早すぎ空白

## ③ 立ち位置
- 実施主体: 個人(ソロ)
- 必然性: ①PayPal sandbox Orders実装経験と資産が直結(技術Edge) ②AP2仕様は公開=仕様由来のシナリオを個人でも実装可 ③審査員(PayPal DevRel/エンジニア)と同型の開発者=自分が対象者の1人目
- 他ではできない理由: 大手テストベンダーは汎用決済テストに注力(エージェント意図の概念なし)。ウォレット勢は発行側で「自分を検査する」立場に立てない

## ④ 価値単位
- 主語: **エージェント決済の適合検査の仕組み**(マンデート注入→sandbox実行→意図適合判定→適合レポート)
- 定義: 「支払いが通ったか」でなく「**頼んだ意図通りに処理されたか**」を検査する層
- 選択理由: 「意図適合」は実取引では意図データが無く検証不能(M5-1が死んだ壁)だが、**テストでは意図を注入する側が持つ=検証可能になる**転換

## ⑤ 人物像(JTBD準拠)
### Primary: agent決済を実装する開発者(自分=N=1実体験 + PayPal DevRel/engと同型)
- 状況: PayPalのagentic系API/Agent Readyでagent決済を実装している最中。「正常に通る」ことは確認できるが、「agentが意図を正しく解釈して処理したか」の確認方法が無い — 手作業でシナリオを考えて叩くしかない
- ジョブ: 機能=実装したagent決済が異常系・意図解釈の誤りを含め正しく動くことを出荷前に検証 / 感情=「本番でagentが変な買い方をしないか」不安の解消 / 社会=「検証済みのagent決済」を作ったエンジニアとしての信頼
- スイッチ: Push=手作業シナリオ作成の手間・異常系の再現困難 / Pull=シナリオ自動生成+意図適合の自動判定 / Anxiety=自前の検査が仕様に沿っているかの不安(→仕様由来シナリオで対応) / Habit=手作業curl+目視確認
- 顧客寿命: AP2標準化・検証ツールが登場するまで。リスク(正直な記録): PayPal自身または大手が出す可能性 — 対抗=ハッカソン自体が「先に作る」の場であり、提出時点で先行が無いのが実態
- 証拠強度: **中** — 自分が実装で同じ困りに当たった実体験+審査員が同型開発者+採用増加は一次情報だが、「他の開発者も同じ困り」は仮説(検証充足計画で代替検証を宣言)

### Secondary: Agent Ready導入を検討する加盟店の技術責任者
- 状況: agent決済の導入を評価中。「導入したら正しく動くか」の社内説得材料が要る
- ジョブ: 機能=導入前の適合検査を非専門でも確認できる形で得る / 感情=見切り発車の不安解消 / 社会=導入判断の裏付けを持つ担当者
- 接続: Primary(開発者)の検査出力=適合レポートがそのままSecondaryの説得材料になる(検査器の出力=証拠)

## ⑥ 問題の質(6属性・出典つき)
| 属性 | 証拠 |
|---|---|
| よくある | **弱い(正直な記録)**: agent決済実装者は現状少ない先行層。ただしハッカソンの対象者=「これから実装する人」なので先行層で成立(領域トリアージ「早すぎ」判定と整合) |
| 増えている | PayPal Agent Ready推進+AP2賛同60社超+「Best Use of Agentic Commerce」賞の存在=採用者(=検証が要る人)が増加方向(一次情報) |
| 急ぐ | agent決済の誤動作は本番で金が動く=出荷前の検証が必然。手作業検証は実装ごとに繰り返す手間 |
| 高くつく | agentの誤購入=実際の請求・紛争。検証にかかる手作業時間+本番での誤動作コスト |
| やらざるを得ない | agent決済を出荷するなら異常系・意図解釈の検証は避けられない(目視確認は代替だが非効率・見落としが残る) |
| 頻繁 | 実装ごと・変更ごとに再検証が要る=繰り返し発生 |
証拠あり: **5/6**(「よくある」は先行層のため弱いと正直に記録)

## ⑦ 利用者制約
- 「血肉になることしかいや」— 提出後も生きる資産(sandbox実行基盤・シナリオ生成器・意図適合判定器・適合レポート生成)を優先し、提出用の使い捨てを最小化する

## 構造破壊の準備(破壊対象の思い込み3つ)
| # | 思い込み | 破壊する構造 |
|---|---|---|
| 1 | 「決済テスト=正常系が通ること」 | agent決済の失敗は通信エラーでなく**意味的な誤処理**(違うもの・違う額・違う相手)。検証の対象はHTTP 200でなく意図適合 |
| 2 | 「支払いの検証=数値の照合」 | 意図は自然言語(「80ドル以内の赤いバッシュ」)=**適合判定には意味評価が要る**(ここがAI荷重の接続点) |
| 3 | 「テストは開発者の中で完結する」 | 検査出力=**適合レポート=第三者に見せられる証拠**(加盟店の導入判断・紛争時の証明に繋がる形) |

## 対象者接点設計(会話の調達経路)
- **対象者未存在の代替検証を事前宣言**: agent決済実装者という「まだ居ない層」への実対話は締切内に調達不能
- **宣言する代替検証**: ①自分=実装者の1人目(agent-pay-guardianで同じ壁に当たった実体験=N=1) ②仮想審査員=PayPal DevRel/eng型(審査基準5項目で攻める) ③sandboxでの実動=製品自体が検証ツールのため、**製品が動く=検証が動く**という自己完結の実演
- 会話10件ルートは取らない: 対象者が先行層のため、規約上の代替検証(早すぎ/アクセス不能型)に該当すると事前宣言

## Gate 0追加確認(提出物型判定): **適用**(核がソフトウェア提出物のため)
| 確認項目 | 対応 |
|---|---|
| 「既存の仕組みで足りる」反論 | 最接近=手作業でのシナリオ確認(curl+目視)・汎用決済テスト。**残る差分**: 意図適合の判定(意味評価)+仕様由来シナリオの自動化+適合レポート生成 — 「手でやればできる」は成立するが、それがまさに手間の本体 |
| 証拠の外部性 | **AP2仕様自体が外部アンカー**(シナリオは自分の着想でなく公開仕様の検証責任由来)+PayPal sandboxの実挙動=第三者発行の結果 |
| 計量の判定主体 | 意図適合判定はAIの意味評価+機械照合(金額・品目・相手先のルール判定)。**循環計量を避けるため、適合の判定基準(何をもって適合とするか)を仕様から先に固定**し、その判定をAIが行う |
| 評価セットの健全性 | シナリオ=AP2仕様の異常系(改ざん・期限切れ・二重・制約未解決)由来=**自己生成でなく仕様由来**。意図の注入=自分が作るが、判定の正解=注入した意図自身=クリーンなラベル |
| 差分の実体対応 | 「意図適合の検査」=マンデート注入器+sandbox実行+意味評価判定器+適合レポートの名指し(抽象の「テスト」でなく) |
| 先行技術スイープ(3層・実施済み) | 上記「競合スイープの検索語と出典」に記録 — **エージェント決済の検証器として空いている**(監視・処理勢はいるが検査器は無し) |
| 空白の理由と土台の実在性 | 空白の理由=AP2が2026-05寄贈の新規格で採用前(=本物の早すぎ)。土台の実在性=**仕様公開+sandbox Orders実在=両方実在**(前2案の「不能域」と違う) |
| 実演入力の外部性 | 注入する意図は自分が作るが、**処理結果=PayPal sandbox発行の実挙動=自己生成でない**(「自分の申立」のループを回避) |
| 外部依存の物理検証(3分類) | ①sandbox Orders=**検証済み**(agent-pay-guardianで実装済み資産あり) ②AP2仕様=公開GitHub=即時確認可 ③PayPal agent toolkit/Agent Ready API=**アクセス確認が要る** →縮退経路: toolkit非公開なら標準Orders+sandbox上でマンデート層を自前モデル化(仕様は公開のため実装可) |
| 本体の最低品質 | 1シナリオ(改ざんマンデート等)を注入→sandbox実行→意図適合の判定→レポート出力まで完走 |

## PayPal技術の荷重(スポンサー必然性の明記)
| 要素 | 荷重の形 |
|---|---|
| PayPal sandbox Orders API | **検査対象の決済レール**(テストが流す先=荷重そのもの) |
| PayPal agent toolkit(orders/disputes/cart) | 検証対象の統合面(Agent Ready採用者がテストする面) |

## 前提の最もリスクの高い仮定
- **「テストハーネス」が審査員の「自分も使いたい」に届くか** — 対象=開発者で「便利」止まりのリスクは残る。対抗=審査員がPayPal DevRel/eng=開発者本人で、agentic commerce採用の障壁=「正しく動くか分からない」を解く器として、スポンサーの推進方向(採用加速)と一致する物語が組めるか
