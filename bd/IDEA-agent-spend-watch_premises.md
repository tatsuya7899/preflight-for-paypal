# 事業設計 前提整理: PayPal使途番人(agent-spend-watch)
Created: 2026-10-11 / モード: 早駆け(提出物型 — PayPal AI Hackathon・締切2026-11-12)
領域トリアージ判定: **条件つき入場**(追補1・支払い発行側は占有6社以上のため監査側に反転。詳細は`GEN-*_candidates.md`)

## ① マクロ環境(早駆け圧縮)
| # | トレンド | アイデアとの接続 | 追/向 | 出典 |
|---|---|---|---|---|

### 先例3社(停止・同型を優先)
| 事業 | 状態 | 同じ/違う | 沈んだ理由の適用可否 |
|---|---|---|---|
| Kite Agent Passport | 活動中 | 同じ「agent支払い+ルール」/違い=発行側(占有者) | 占有のため発行側には入らない(監査側に反転済み) |
| Earny(返金自動化) | 停止 | 同じ「支払い後の監視→アクション」/違い=カード価格保証 | 停止理由=収益化難。自案は監査基盤で収益より資産化を優先 |
| Mint(家計簿) | 停止(2024) | 同じ「取引の見える化」/違い=銀行連携・PayPal自動請求の語彙なし | 大手撤退=隙間。ただし「見える化だけでは死ぬ」証左=監査+アクションに寄せる |

## ② 領域スコープ
- 関連領域: PayPal口座の監査 / agent支払いの観測 / 自動請求・定期課金の管理 / 支出異常検知 / 証拠・紛争準備
- 選択スコープ: **自分のPayPal口座の「引き出し監査」**(agent起点・自動請求・定期課金を問わず「何が・なぜ・どこから引いたか」の発生元特定+異常検知+証拠束生成)
- 選択理由: 発行側(ウォレット)は占有6社以上・買い手側データは本人にしか届かない=「本人側監査」が唯一Edgeの荷重が利く空き地

## ③ 立ち位置
- 実施主体: 個人(ソロ)
- 必然性: ①買い手側PayPalデータに第三者APIが届かない=**本人の拡張機能/エクスポート経由でしか読めない**=本人が自分のデータで作る必然 ②PayPal sandbox Orders実装経験+拡張機能実装力(技術Edge) ③agent商取引の占有地図を持つ(市場Edge)
- 他ではできない理由: 大手は買い手側データに届かない・ウォレット勢は自社レールの監査のみ(他社レール・自己申告の対象外)

## ④ 価値単位
- 主語: **自分の口座の引き出し監査の仕組み**(取引の発生元特定・異常検知・証拠束生成)
- 定義: 「お金を払う」でなく「**払われた後に、誰が何のために引いたかを口座側で検証し記録する**」層
- 選択理由: 発行側は占有・監査側は自己申告しか無い=「第三者発行の取引記録と突合する監査」が実体のある差分

## ⑤ 人物像(JTBD準拠)
### Primary: 自分(N=1実体験)
- 状況: 月末または「PayPalでお支払いがありました」メールを見たとき、口座画面を開いて引き出しの内訳を手で突き合わせている。agent系・自動請求が増えるにつれ「何が何を引いたか」の判別がつかなくなる
- ジョブ: 機能=引き出しの発生元を即座に特定し異常を早期発見 / 感情=「気づかないうちに金が出ていく」不安の解消 / 社会=資金をAIに任せつつ「管理している」立場を保つ
- スイッチ: Push=手突合の手間・発生元不明の不安 / Pull=自動監査+発生元の説明付き / Anxiety=誤検知・監視自体の手間 / Habit=PayPal画面の目視
- 顧客寿命: **ウォレット勢が監査を内蔵するまで** — 寿命リスク(正直な記録): Kite等がダッシュボード内蔵済み。対抗=「ウォレット提供元の台帳は自己申告・PayPal側の実取引と突合する第三者監査」は内蔵品では実現できない(自分の口座を自分で監査するのが監査の本来形)
- 証拠強度: **中** — 自分の実体験+agent決済の増加は一次情報だが、「他の個人も同じ困りを持つ」は仮説(検証充足計画で代替検証を宣言済み)

## ⑥ 問題の質(6属性・出典つき)
| 属性 | 証拠 |
|---|---|
| よくある | 「PayPalからagent/自動請求が引く対象者」は現状少ない — ただしPayPal自動支払い・Braintree請求等の実取引対象は既に存在(成長中の先行層と正直に記録) |
| 増えている | agent決済ウォレット勢6社+スポンサー推進+「Best Use of Agentic Commerce」の賞が存在=監査対象は増加方向 |
| 急ぐ | 誤請求・暴走は発生後しか気づけない=監視が先に要る |
| 高くつく | 手突合の時間+気づかない損失(実測未実施・勘) |
| やらざるを得ない | 放任=資金流出(放置コスト) |
| 頻繁 | 請求は月次〜随時(自分の取引履歴で実測可) |
証拠あり: 4/6程度と自己評価

## ⑦ 利用者制約
- 「血肉になることしかいや」— 提出後も生きる資産(取引解析・異常検知・証拠束生成・拡張基盤)を優先し、提出用の使い捨て部品を最小化する

## Gate 0追加確認(提出物型判定): **適用**(核がソフトウェア提出物のため)

| 確認項目 | 対応 |
|---|---|
| 「既存の仕組みで足りる」反論 | 最接近=ウォレット勢の内蔵ダッシュボード(Kite等・自己申告)・支出管理アプリ・PayPal標準通知。**残る差分**: 「発行元の自己申告台帳」ではなく「PayPal取引記録(第三者発行)との突合監査」+「自分の口座を自分で監査する」形 |
| 証拠の外部性 | **PayPal取引記録=第三者発行アンカー**(agent-pay-guardianが欠いていた外部アンカーが本件では自然に取れる) |
| 計量の判定主体 | 異常検知はルール+閾値の機械判定(正解ラベル=自分の実取引の発生元属性)。循環計量を避けるため「agent/自動請求/定期課金」の分類境界は文書で先に固定する |
| 評価セットの健全性 | 自分の実取引データ+実在の請求パターン(自動支払い・定期課金の実物)。自己生成シナリオは避け、PayPal発行の実データを使う |
| 差分の実体対応 | 「PayPal実取引×発生元属性の突合」=拡張機能での口座読取り+取引パーサ+発生元分類器+証拠束生成器の名指し |
| 先行技術スイープ(3層・実施済み) | ①規格・大手: PayPal agentic系は加盟店側(買い手側監査APIなし) ②同規模: ウォレット勢6社は発行側・監査は内蔵dashboard(自己申告) ③同型: 家計簿/支出管理は銀行連携前提・PayPal引き出しの発生元特定は空。**「agent引き出しの口座側監査」は空いている** |
| 空白の理由と土台の実在性 | 空白の理由=agent決済が未成熟(早すぎ)+第三者が消費者データに届かない(不能域)→**拡張機能+自己データで迂回可**(土台=自己データは実在) |
| 実演入力の外部性 | 自分の実PayPal取引=PayPal発行で**自己生成でない**(「自分の店・自分の金・自分の申立」の自己申告ループを回避) |
| 外部依存の物理検証(3分類) | ①拡張での口座読取り=即時検証可 ②取引エクスポート=即時 ③agentサービスの実請求データ=観測機会依存→**縮退経路=自動請求系の実取引で代替**(agent支払いに限らず引き出し監査全般として設計) |
| 本体の最低品質 | 実取引で「検出→発生元の説明→証拠束生成」まで完走 |

## 前提の最もリスクの高い仮定
- 「自分の口座を自分で監査する価値」が審査員の「自分も使いたい」に届くか(「ウォレット勢の内蔵dashboardで足りるのでは」への反論が成立するか)
