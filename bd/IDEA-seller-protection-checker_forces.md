## 技法44 悩みの分割(事業層・表面→根本の順で7件)

1. Seller Protectionの条件(指定住所発送・追跡情報・除外品目・金額閾値)を細部まで覚えていない — 記憶負荷(premises §⑤: 「細部まで覚えていない」)
2. 取引詳細の旗を見ても対象外の**理由**が分からない — 可視性の欠如(premises先例: 「旗は出すが理由と処方は出さない」=事実)
3. PayPalがshipping省略時に買い手既定住所を自動注入するため「住所が見える=確認済み住所」が成立しない — データの見えと規約意味の乖離(premises 実測の追加発見=事実)
4. 条件は注文ごとに変わる(品目・金額・住所)のに規約は散文=毎回の照合作業が残る — 翻訳層の欠如(dtf バイアス4)
5. 詐欺パターン文書(住所変更要求・前払いラベル・過払い)と保護条件が別文書で、注文への統合照合がない — 照合コスト(premises 構造破壊3)
6. 追跡番号のPayPal登録が別作業で、診断→処置が繋がっていない — 処置の分断(実測: trackers-batch APIは実在するが手動工程=premises 書き込み実測)
7. **根本: 「この出荷行為が保護条件を満たしているか」が、行為と結びついて見えない** — 旗(宣言値スナップショット)と行為条件の乖離が不可視(dtf バイアス5・レバーC=製品の中身そのもの)

## 技法45 悩みの根っこ(なぜ×5 + 代替ルート棄却検討)

### なぜ×5(対象: 分割7「対象外のまま出荷して紛争で負ける」)

1. なぜ対象外のまま出荷するか → 対象外だと**気づかない**から
2. なぜ気づかないか → PayPalの旗はELIGIBLEと言うが、行為条件(指定住所・追跡・除外品目・リダイレクト禁止)は旗の定義域外に残るから(事実: premises 仮想審査員再判定「旗は前提条件のスナップショット」+ sandbox実測で条件変動しても常時ELIGIBLE)
3. なぜ行為条件が見えないか → 条件は規約文(散文)にあり、API構造化データへの翻訳層が無いから(dtf バイアス4)
4. なぜ翻訳層が無いか → PayPalが診断を提供しないのは構造的意志決定(「今この取引は条件を満たす」と開示すると裁定責任を問われる)だから(dtf 見えない力学)
5. なぜ構造的に提供されないままか → 保険者自身が裁定者であり、事前適合の開示は自らの裁量を縛るから=**第三者が供給するしかない空隙**が構造的に固定されている

### 代替ルート(なぜ×5の「製品が要る」鎖と競合する説明・棄却理由つき)

| ルート | 説明 | 棄却判定 | 棄却理由/残余 |
|---|---|---|---|
| A. 痛み不在 | 紛争率<1%(premises審査員指摘=事実)で大多数のセラーは痛みを一度も経験していない。Pushの実在自体が未証明 | **棄却不能** | 会話0件・セラーが事前チェックを実際に行っているかの行動証拠なし。**検証仮説の最優先項**(§検証仮説へ引き継ぎ) |
| B. 別主体の問題 | 詐欺・裁定はPayPalが吸収すべき問題で、セラーは自分の作業と認識していない可能性 | 一部棄却 | PayPal公式が「出荷前に自分で注文を確認せよ」とセラー側作業として課している(事実: premises ①)=責任はセラー側。ただし「セラーがそれを自分の問題と認識しているか」は未検証で残余 |
| C. 既存代替で充足 | Guzco(事前チェック機能)・SyncPal(追跡)で既に解決済み | 長尾層では棄却可能 | Guzco=DFYサービスで料金形が長尾に見合わない・SyncPal=診断なし(事実: dtf占有スイープ)。**ただし中規模層では棄却不能**=ターゲットを長尾に限定する根拠 |
| D. 能力差の問題 | 英語規約を読めない/面倒なだけで、ツールでなく学習で解決する | 棄却可能(弱) | 条件照合は注文ごとの反復作業(品目・金額・住所が変わる)で一回の学習では終わらない。ただし「学習すれば足りる」が真でも診断ツールの需要は残る=棄却できるが決定的でない |

**結論(単数形禁止に従い複数形)**: 根っこは2つ残る — (a)「行為条件の不可視は構造的空隙」(事実側・製品の存在理由)と、(b)「その不可視をセラーが痛みとして感じているかは未検証」(ルートA残余・事業側の最大の不確実性)。提出物層では(a)のみで採点面が立つ。事業層では(b)が埋まるまでPushを◎と主張できない。

## 4つの力 — 事業層(実PayPalセラー)

### Push 強度: △(仮説・条件つきで○)
- 不満: 対象外のまま出荷→商品+金の全損(事実: premises 高くつく)/ 「自分で確認せよ」の日次手作業が課されている(事実: PayPal公式要求)
- 頻度: 受注ごと(事実)。ただし**痛みの顕在化は紛争時のみで紛争率<1%**(**仮説**: 仮想審査員の言明由来・一次出典未確認=要一次確認)=「深刻だが散発的」
- 深刻度: 発生時は致命的/非発生時は不可視
- 証拠区分: 損失の構造・手作業の存在=**事実**。セラーが痛みを**感じている**か=**仮説(会話0件・ルートA未棄却)**

### Pull 強度: ○(仮説)
- 機能的価値: 出荷前に「対象外の理由+対象に戻す処方」/ ELIGIBLEでも詐欺パターン一致ならDON'T SHIP(事実: premises審査員条件②)
- 感情的価値: 「PayPalに守ってもらえる取引をしている」安心(premises §⑤)
- ジョブ完了力: 診断→追跡登録→再検証の閉ループが全て実APIで構成可能(事実: premises tracking実測)

### Inertia 強度: ◎(仮説)
- 慣れ: 「取引詳細を目視するが細部は読まない」習慣(事実: premises §⑤ Habit)
- **サバイバーシップ: 紛争率<1%(仮説・出典未確認)が真なら「今まで大丈夫だった」を大多数のセラーに供給し続ける=現状維持バイアスの最大の供給源**(構造的推論・前提が仮説)
- 学習コスト: コンソール拡張の導入・画面の見方=小〜中(仮説)
- サンクコスト: 既存出荷フローへの組み込み無し=低(仮説)

### Friction 強度: ○(仮説)
- 導入コスト: PayPalアカウント接続(read系)+コンソール拡張の設置(仮説)
- 失敗リスク: **誤診不安=「対象と誤判定して実は対象外」**(premises §⑤ Anxiety・対策=判定はルール層決定的・AI層は説明のみの2層設計=事実として設計済み)
- 「APIに無いものは見えない」の正直表示で信頼を稼ぐ設計(事実: premises審査員条件⑤)
- 失敗時に戻せるか: 診断ツールは既存フローを変えない付加層=戻しやすい(構造・仮説)

- 説明力: 「Guzco=DFYサービスの一機能 vs 弊案=コンソール内在セルフサーブ製品」の棲み分けが60秒で伝わる(事実: dtf §射程)

### Inertia 強度: △(仮説)
- 採点基準への忠実さ=むしろ推進側に働く(基準が実演・スポンサー荷重を見る限り)。先入観「旗があるから十分」は抵抗力側(仮説)

### Friction 強度: ○(仮説・対策設計済み)
- 「スタブが言ってるだけ」と読まれるリスク → 対策=旗との裸の対置禁止・常時「declared-data snapshot」ラベル併記(事実: premises最終判定の文言規律)
- 「規約解釈を間違える」のリスク → 対策=処方は固定表・LLMに規約解釈させない(事実: premises審査員条件③)
- 「あなたは負けます」の過剰主張禁止 → 言えるのは「PayPalが要求した証拠=我々が警告した証拠」まで(事実: 文言規律)

## バランス判定 — 提出物層

```
Push [○] + Pull [◎]  vs  Inertia [△] + Friction [○]
    推進力 合計 [◎]           抵抗力 合計 [○]

スイッチ判定: 発生可能・条件つき — 条件はpremises残条件の遵守
(3幕構成・無争議症例のみ・US規約ピン・裸対置禁止・文言規律)。
```

## 介入戦略

### 提出物層(主戦場)
| 介入先 | 具体策 | 整合性チェック |
|---|---|---|
| Pull強化 | act-3で「我々が警告した証拠種別 = PayPal機械が実際に要求したevidence_type」を1対1で並置(premises デモ台本) | ✅ 製品の定義特性(旗乖離の露出+警告の正当性)を強化する方向 |
| Friction低減 | 旗を表示から**外す**案 → **棄却**: 乖離の露出は旗の並置があって成立する製品の定義特性。外すと「別製品」(自社スコア表示器)になる。**代替: 旗は常時「declared-data snapshot」ラベル付きで並置し、診断は旗の定義域外に配置**(premises禁止事項の遵守) | 定義特性の一時停止を回避した摩擦低減 |
| Inertia低減 | 冒頭60秒で「Guzco=DFY一機能 vs 弊案=コンソール内在セルフサーブ」の棲み分けを先に言う(dtf 60秒説明力) | ✅ |

| 介入先 | 具体策 | 整合性チェック |
|---|---|---|
| Inertia低減 | 新規画面でなく**取引詳細の閲覧フローに内在する拡張**(premises 対象者接点設計「警戒している必要がない到達形」) | ✅ 定義特性(まだ間に合う瞬間の介入)と一致 |

## 代替検証(実セラー実演)の調達経路【Gate 2レビュー指摘・追加】

- **対象**: 実在のPayPalセラー1名(事前宣言ルート=One-Person Test相当)
- **母数スクリーナー(先頭質問)**: 「PayPalで物販の受注をしたことがありますか?」— Yes以外は非対象として会話から除外(phase2規約どおり行動形質問の前に母数実在を測る)
- **調達チャネル候補**: ①利用者の知人・取引先のネットショップ運営者 ②X/掲示板の個人商店コミュニティ(メルカリ・BASE・Shopify運営の声が出る場) ③ハッカソンコミュニティ内の出店経験者
- **逆算期限**: 締切2026-11-12。実演→結果記録→デモへの反映で最低3日見て**11/09までに相手確保**が安全側。調達失敗時は検証充足計画どおり「未検証のまま提出」が既定(虚偽しない)
- **実演の形**: 実装済み拡張(またはfixtureデモ)を使ってもらう。**相手の本番注文はsandboxに入らない制約があるため、相手の直近実注文データをパラメータ化してsandbox再現した注文(実注文相当)で実演する**。成功シグナル=「ハッカソン後も使い続けていい?」と自発的に聞かれるか
- **依存**: **相手の調達は人間(利用者)の行動が必須** — AI側で完結できない唯一の工程。ここが詰まった場合の退避路は検証充足計画の事前宣言どおり(条件付きで進み「未検証」を提出物に正直表示)

## 検証仮説(dtf §Phase 2への引き継ぎへの応答)

1. 「小規模セラーは出荷前に条件を教えてほしいPushを持つか」→ **未検証(ルートA残余=最優先)**。代替検証=実セラー実演で確認
2. 「Guzcoの料金が見合わない層に届くか」→ 構造的には立つ(事実: DFY形の価格不整合)が到達経路=**証拠なし**
3. 「旗がELIGIBLEでも条件が欠ける経験の実在性」→ 乖離の**構造的存在は実測済み**(sandbox旗スタブ+既定住所自動注入=事実)。セラーがそれを**経験として認識しているか**は**証拠なし**
