# 1枚回答: Preflight for PayPal(Seller Protection適合チェッカー)
Created: 2026-10-11
Input: `_fermi.md` / `_canvas.md` / `_forces.md` / `_premises.md`(yc-lens.md §4の7問・各2文以内・抽象語不使用)

1. **何を作るか**: PayPalで物販を受ける小規模セラー向けに、出荷前に「この注文はSeller Protectionの対象外」と、その条件名と対象に戻す修正方法を表示するブラウザ拡張。

2. **誰が使っていて、何人か**: 実利用者は0名で、会話した相手も0件(自分のネットワーク内に対象者がいないアクセス不能型)。代替検証として11/09までに実在セラー1名へ、相手の直近実注文をsandbox再現した注文(実注文相当)での実演を計画済みで、相手の調達だけが利用者の行動に依存する。

3. **なぜ今か**: PayPalがorders/shipment/Disputes APIを公開しsandboxで紛争の証拠要求と資金保留まで全工程が動くことを実測で確認した(2026-10-11)のに、保護条件の照合は規約散文を読む手作業のまま残っている。提出期限2026-11-12のハッカソンが「今作る」期限を固定している。

4. **何に気づいたか**: PayPalの対象旗は宣言値のスナップショットで、出荷行為の条件(指定住所発送・追跡・除外品目)を見ない — sandboxで条件を最大限変えても常時ELIGIBLEを返すことを実測した。「旗が言う適格」と「行為が満たす条件」の乖離そのものを取引単位で表示する製品は見つかっていない。

5. **競合は誰で、なぜ勝てるか**: 競合はGuzco(代行型の紛争対応サービスの一機能として事前チェック。料金形が長尾に見合わない)とSyncPal・TrackiPal系(追跡番号の自動同期のみで診断しない)。勝てるとすれば「PayPalコンソール内在・セルフサーブ・旗との乖離をその場で出す」の組合せだけで、規約写像の堀は弱い(模倣可能)と自覚している。

6. **どう稼ぐか、または価値をどう測るか**: 賞金でなく継続条件で測る — Devpost公開結果での入賞、または実セラー1名が実演後に「使い続けていい?」と自発的に尋ねること。1セラーあたりの年間価値は手作業削減と対象外損失(商品+送料+代金+紛争手数料の全損)の回避で$9〜$7,200の帯(係数は勘と未検証の仮説)。

7. **最初に作るものは何か**: sandbox実注文で診断→警告→追跡番号登録→再検証を実APIで完走する3幕デモ(部品は全て実測済み・組立てが残務)。相手の「欲しい」は、実セラー実演で継続利用を自発的に尋ねられるかをもって初めて確認する。
